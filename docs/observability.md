# Observability

StoreControl combines structured logs, W3C distributed traces, bounded-cardinality metrics and health checks. The goal is to explain a failure across boundaries without recording request bodies, credentials, tokens or business payloads.

## Local stack

The default Compose stack includes the standalone .NET Aspire Dashboard. It receives OTLP logs, traces and metrics from API and Worker and is available at `http://localhost:18888`. Its anonymous mode is acceptable only because the published port is bound to `127.0.0.1`; this configuration is not a production deployment.

Inside Compose, both processes use `OpenTelemetry__OtlpEndpoint=http://aspire-dashboard:18889`. For hybrid execution, `scripts/Set-LocalEnvironment.ps1` points them to the loopback OTLP gRPC port, `http://127.0.0.1:4317` by default. An empty `OpenTelemetry:OtlpEndpoint` disables export but does not disable instrumentation. A configured non-absolute URI fails startup instead of silently losing telemetry.

To inspect a flow locally:

1. start the stack with `docker compose up --build`;
2. perform the operation in the Web application;
3. copy `X-Trace-ID` and `X-Correlation-ID` from the HTTP response in Browser DevTools;
4. open the dashboard, select Traces and search for the trace ID;
5. use structured Logs with the same trace or correlation ID, then inspect Metrics for aggregate behavior.

## Correlation and trace identity

These identifiers serve different purposes:

- `X-Correlation-ID` is an application identifier. Axios creates it once and preserves it across an authentication retry. The middleware validates its character set and maximum length, generates a replacement when invalid and returns it on every response.
- `traceId` is the 32-hex-character W3C distributed trace identity generated by `Activity`. It is returned as `X-Trace-ID` and in Problem Details. `spanId` identifies one operation inside that trace.
- `Idempotency-Key` is a business-command identity. It prevents duplicate effects and must not be confused with either diagnostic identifier.

Serilog scopes contain `CorrelationId`, `TraceId` and `SpanId`. The HTTP trace also carries `storecontrol.correlation_id`, which makes either identifier a useful entry point. CORS exposes the two diagnostic response headers to the React origin.

## End-to-end sale trace

The synchronous section has one ASP.NET Core server span, one explicit business span and child SQL Client spans:

    Browser POST /api/sales
    → ASP.NET Core request span
      → SalesController
      → sale.finalize (StoreControl.Business)
        → SaleService / Domain rules
        → EF Core
        → Microsoft.Data.SqlClient spans
        → sales + inventory + cash + integration.OutboxMessages
      → SQL commit
    → HTTP response with X-Correlation-ID and X-Trace-ID

Controller and EF Core method boundaries are intentionally not wrapped in mechanical spans. The HTTP, `sale.finalize` and SQL spans show the meaningful latency boundaries. The business span records store/operation/sale identifiers, committed total, replay state and bounded outcome; it does not record customer, payment reference or cart payload.

The Outbox persists `traceparent`, optional `tracestate` and correlation ID with the event. This preserves the causal trace across polling delay and process boundaries:

    integration.OutboxMessages
    → API RabbitMQ producer span
    → traceparent/tracestate RabbitMQ headers
    → Worker RabbitMQ consumer span (remote parent)
      → SqlClient spans
      → integration.InboxMessages + SaleReceiptDeliveries
    → SQL commit
    → manual acknowledgement

Retry publication is a child producer span. The next delivery continues from its propagated remote parent. A duplicate delivery therefore has a new branch in the same causal trace while Inbox still prevents another database effect.

## Logs

Serilog writes compact JSON to stdout. The OpenTelemetry logging provider exports formatted messages and scopes when OTLP is configured. Resource attributes distinguish `StoreControl.Api` and `StoreControl.Worker`, application version, process instance and environment.

Useful Information logs describe durable transitions: sale committed, cash opened/closed, Outbox publication confirmed and Worker processing outcome. Expected 4xx business rejections are Warning; unexpected 5xx failures include the exception once at the API boundary. Successful health-request logs are Debug to avoid probe noise. EF command logs remain Warning by default because traces already show database latency.

Never add the following to templates, scopes, tags or exceptions intended for export:

- passwords, JWTs, refresh tokens, cookies or signing keys;
- connection strings or RabbitMQ/Redis credentials;
- request/response bodies and event payloads;
- customer contact data, payment references or raw Redis keys;
- SQL parameter values.

SqlClient parameter capture remains disabled. SQL commands are parameterized throughout the application; do not introduce literal sensitive values into direct SQL.

## Traces

API instrumentation includes ASP.NET Core requests, outgoing HTTP, SqlClient, cache, dependency health, messaging and business activities. Worker instrumentation includes SqlClient, messaging and dependency sources. Both force W3C IDs.

Important activity sources:

| Source | Operations |
| --- | --- |
| `StoreControl.Business` | `sale.finalize` |
| `StoreControl.Cache` | `cache.get`, `cache.set` |
| `StoreControl.Messaging` | RabbitMQ producer, retry producer and consumer |
| `StoreControl.Dependencies` | `dependency.health.check` |

Errors set span status and an exception type, not the exception message. The normal ASP.NET Core and SqlClient instrumentation supplies transport/database spans around these explicit business boundaries.

## Metrics

Metric dimensions use controlled values only; correlation, trace, sale, message and store IDs are intentionally excluded from metric labels.

| Instrument | Meaning and principal labels |
| --- | --- |
| `storecontrol.sales.finalizations` | committed, replayed, validation, conflict, not-found, canceled or failed sale attempts |
| `storecontrol.sales.total` | BRL value of newly committed sales; replays do not count again |
| `storecontrol.business.operation.duration` | sale finalization duration in seconds by bounded outcome |
| `storecontrol.cache.requests` | cache outcome by region |
| `storecontrol.cache.redis.duration` | Redis operation duration |
| `storecontrol.messaging.publications` | confirmed/failed publishes |
| `storecontrol.messaging.publish.duration` | publisher-confirm path duration |
| `storecontrol.messaging.deliveries` | processed/duplicate/retry/dead-letter outcomes |
| `storecontrol.messaging.consume.duration` | end-to-end duration of one delivery attempt |
| `storecontrol.dependencies.health_checks` | health result by dependency |
| `storecontrol.dependencies.health_check.duration` | health-check duration by dependency/result |

ASP.NET Core request and .NET runtime metrics are also exported. Metrics are diagnostic measurements, not accounting records; SQL ledgers remain authoritative.

## Health checks

Public payloads contain aggregate status only and set `Cache-Control: no-store`:

- `/health/live`: process liveness, without dependency checks;
- `/health/ready`: SQL Server readiness;
- `/health/cache`: Redis status; unavailable Redis is Degraded while SQL fallback remains available;
- `/health/messaging`: RabbitMQ status; unavailable RabbitMQ is Degraded while the SQL Outbox preserves committed events;
- `/health`: aggregate registered dependencies.

A disabled optional subsystem reports Healthy because that mode is intentional. The authenticated `/api/smoke` endpoint is the place for foundation version and database time. Health endpoints should not expose hostnames, connection strings, exception details or credentials.

## Sampling and production boundary

The local dashboard is designed for study and short-lived diagnostics. Production would require authenticated telemetry storage, TLS, retention, resource limits, sampling and redaction review. IDs belong in trace/log fields, not metric labels. Raising EF or framework logs to Debug should be temporary and narrowly scoped.
